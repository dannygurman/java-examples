1. COLLECTIONS: List / ArrayList / Map / HashMap / HashSet
--------------------------------------------------------------------------------

Q: What is the difference between List, ArrayList, Map, HashSet and HashMap?

ANSWER
  List        Interface. Ordered, duplicates allowed, access by index.
  ArrayList   List implementation backed by an array.
              get O(1), add amortized O(1), insert/remove in the middle O(n).
              Not thread-safe.
  Map         Interface. Key -> value, unique keys. NOTE: Map is NOT a
              Collection - it sits outside the Collection hierarchy.
  HashMap     Map implementation using hash buckets.
              Average O(1) get/put, no ordering guarantee, allows one null key
              and many null values. Not thread-safe.
  HashSet     Set implementation backed internally by a HashMap.
              Unique elements, no ordering, O(1) contains.

  Also worth knowing: LinkedList (O(1) insert at ends, O(n) index access),
  LinkedHashMap (insertion order), TreeMap (sorted, O(log n)),
  ConcurrentHashMap (thread-safe).

FOLLOW-UPS
  - What contract must a key satisfy to work in a HashMap or HashSet?
    (Consistent equals/hashCode; equal objects must have equal hash codes.)
  - What happens if you mutate a key after putting it in a HashMap?
    (You can no longer find it - it hashes to a different bucket.)
  - ArrayList vs LinkedList - when would you choose each?
  - How does HashMap handle collisions?  (Chaining; converts a long bucket
    chain to a balanced tree since Java 8.)

RED FLAGS
  - Thinking Map extends Collection.
  - Not knowing why equals/hashCode matter.
  - Claiming HashSet preserves insertion order.

2. ERROR vs EXCEPTION - CHECKED vs UNCHECKED
--------------------------------------------------------------------------------

Q: What is the difference between an Error and an Exception? What are checked
   and unchecked exceptions?

ANSWER
  Both Error and Exception extend Throwable.

  Error
    JVM or environment failure that you should not try to catch.
    Examples: OutOfMemoryError, StackOverflowError, NoClassDefFoundError.

  Exception
    Application-level problem.

    Checked   - everything under Exception except RuntimeException.
                The compiler forces catch-or-declare.
                Examples: IOException, SQLException, InterruptedException.

    Unchecked - RuntimeException and its subclasses.
                Usually programming bugs. No declaration required.

  SUB-QUESTION: Are there exceptions that are unchecked?
    Yes - RuntimeException and all its subclasses, plus everything under Error.
    Examples: NullPointerException, IllegalArgumentException,
    IllegalStateException, ArrayIndexOutOfBoundsException, ClassCastException,
    NumberFormatException, ArithmeticException,
    UnsupportedOperationException, ConcurrentModificationException.

FOLLOW-UPS
  - What is wrong with "catch (Exception e) {}"?
  - What does finally guarantee, and when does it not run?  (System.exit, JVM
    crash; also a return in finally swallows the exception.)
  - What is try-with-resources and what problem does it solve?
  - Checked vs unchecked in API design - which would you throw and why?

RED FLAGS
  - Catching and swallowing exceptions silently.
  - Catching Throwable or Error.
  - Not knowing that RuntimeException is unchecked.

3. THREADS - BASICS
--------------------------------------------------------------------------------

Q: How do you create and start a thread? What is the difference between start()
   and run()? What does synchronized do?

ANSWER
  Creating
    - Implement Runnable and pass it to a Thread (preferred - composition,
      not inheritance), or subclass Thread.
    - In real code you rarely do either: use an ExecutorService from Executors
      so threads are pooled and reused. (Java 21+: virtual threads.)

  start() vs run()   - the classic trap
    - start() asks the JVM for a NEW OS thread and calls run() on it.
    - Calling run() directly just executes the method on the current thread -
      no concurrency at all.
    - Calling start() twice throws IllegalThreadStateException.

  Thread states
    NEW -> RUNNABLE -> (BLOCKED / WAITING / TIMED_WAITING) -> TERMINATED
    BLOCKED = waiting for a monitor lock.
    WAITING = wait() / join() with no timeout.

  synchronized
    - Mutual exclusion: one thread at a time per monitor object.
    - Visibility: everything written before releasing the monitor is visible to
      the next thread that acquires it.
    - On an instance method the monitor is "this"; on a static method it is the
      Class object.

FOLLOW-UPS
  - What is a race condition? Give an example.
  - What is a deadlock and how do you avoid it?  (Consistent lock ordering,
    timeouts, fewer locks.)
  - Why is Thread.stop() deprecated?  (Leaves objects in an inconsistent state;
    use an interrupt flag instead.)
  - wait() vs sleep()?  (wait() releases the lock, sleep() does not.
    wait() must be called while holding the monitor.)

RED FLAGS
  - Calling run() instead of start().
  - Believing synchronized on two different objects provides mutual exclusion.
  - Never having heard of a thread pool.

4. THE "volatile" KEYWORD
--------------------------------------------------------------------------------

Q: Explain volatile. When would you use it?

ANSWER
  Guarantees
    - Visibility: writes go to main memory, reads are never taken from a
      CPU-local cache. Other threads always see the latest value.
    - Ordering: forbids reordering of instructions around the access.

  Does NOT guarantee
    - Atomicity. "count++" is a read-modify-write and is still broken with
      volatile.

  When to use it
    - A stop / state flag written by one thread and read by others.
    - The field in a double-checked-locking singleton.

  When NOT to use it
    - Counters -> use AtomicInteger.
    - Compound state that must change together -> use a lock.

FOLLOW-UPS
  - Why is "volatile boolean running" a valid stop flag but "volatile int
    counter" a broken counter?
  - What is the difference between volatile and synchronized?  (volatile gives
    visibility only; synchronized gives visibility AND mutual exclusion.)

RED FLAGS
  - "volatile makes operations atomic" or "volatile is a lightweight lock".

5. JVM MEMORY: HEAP vs NON-HEAP
--------------------------------------------------------------------------------

Q: What lives in the heap versus outside it, and which OutOfMemoryError comes
   from where?

ANSWER
  One OS process, one virtual address space:

    JVM process (what the OS sees as RSS)
     |- Java heap                  <- bounded by -Xmx, GC-managed
     |- non-heap
         |- Metaspace
         |- thread stacks
         |- code cache
         |- GC's own structures
         |- direct / native memory <- malloc'd, not GC-managed

  HEAP
    All objects and arrays. Managed by the garbage collector.
    Split into Young (Eden + 2 Survivor spaces) and Old / Tenured. Most objects
    die young; survivors are promoted. Sized with -Xms / -Xmx.
    Exhaustion -> OutOfMemoryError: Java heap space

  NON-HEAP  (not counted in -Xmx)
    Metaspace       Class metadata. Replaced PermGen in Java 8.
                    -> OutOfMemoryError: Metaspace
    Thread stacks   One per thread: frames, local variables, primitives, and
                    object *references*.
                    -> StackOverflowError; "unable to create new native thread"
    Code cache      JIT-compiled native code.
                    -> "CodeCache is full"
    Direct/native   ByteBuffer.allocateDirect, NIO, Netty, JNI libraries,
                    memory-mapped files.
                    -> OutOfMemoryError: Direct buffer memory

  Key points to listen for
    - A primitive declared as a local variable lives on the stack, but a
      primitive *field* lives inside its object on the heap.
    - -Xmx is not the container memory limit. Total RSS = heap + metaspace +
      stacks + code cache + direct buffers. A container whose limit equals -Xmx
      will get OOM-killed.
    - "Native memory" is still RAM, allocated by malloc rather than by the JVM
      heap allocator. It is part of the JVM *process*, not the JVM *heap*.
      The GC cannot see it; it is freed by a Cleaner, close(), or native code.
      This is why a native leak is invisible in a heap dump - use
      -XX:NativeMemoryTracking=summary and "jcmd VM.native_memory".

  Bonus: escape analysis / scalar replacement can keep short-lived objects off
  the heap entirely.

FOLLOW-UPS
  - What causes a StackOverflowError?  (Deep or infinite recursion.)
  - What is the difference between the stack and the heap for a local variable
    holding an object?  (Reference on the stack, object on the heap.)
  - Roughly how does a generational GC work?

RED FLAGS
  - Believing -Xmx caps total JVM memory.
  - "Objects can be on the stack" with no mention of escape analysis.

6. DEFAULT METHODS IN INTERFACES (and the diamond problem)
--------------------------------------------------------------------------------

Q: What is a default method? What is it good for, and what is its main problem?

ANSWER
  What
    An interface method with a body, added in Java 8.

  Why
    Lets you evolve an interface without breaking every existing implementor.
    That is how Collection.stream() and Iterable.forEach() were added to the
    JDK without breaking the world.

  The problem - the diamond
    If a class implements two interfaces that both declare the same default
    method, it is a COMPILE ERROR. The class must override the method and
    resolve it explicitly:

        class C implements A, B {
            public void m() {
                A.super.m();   // pick one explicitly
            }
        }

  Resolution rules
    1. A class implementation always wins over an interface default.
    2. A more specific interface (a sub-interface) wins over a less specific one.
    3. Otherwise -> compile error, you must override.

  SUB-QUESTION: Does a default method have state?
    NO. An interface cannot have instance fields. The only fields allowed are
    implicitly public static final constants - shared by everyone, not per
    object state.

        interface A {
            int MAX = 10;          // implicitly public static final
            // int count;          // COMPILE ERROR - no instance fields
            default int next() { return MAX + 1; }
        }

    A default method can only work with:
      - the interface's constants,
      - its own parameters and local variables,
      - other methods called on "this" (abstract or default).

    This is exactly why Java can allow "multiple inheritance of BEHAVIOUR"
    without the classic C++ multiple-inheritance mess: you inherit code, never
    fields. There is no ambiguity about which copy of a field you own, because
    there are no fields. The only conflict left is which method body to use -
    and the compiler forces you to resolve that explicitly.

    If you need state, put it in the implementing class (or use an abstract
    class, which CAN have instance fields and a constructor).

  Abstract class vs interface (quick contrast)
    Interface       no instance state, no constructor, multiple inheritance,
                    default/static/private methods, members implicitly public.
    Abstract class  instance fields, constructors, any access modifier,
                    but a class can extend only ONE.

FOLLOW-UPS
  - Can a default method be final or synchronized?  (No.)
  - Can an interface provide a default implementation of equals/hashCode/
    toString?  (No - Object methods cannot be defaulted.)
  - Does a default method break a functional interface?  (No - only abstract
    methods count toward the single-abstract-method rule.)

RED FLAGS
  - "Java now has multiple inheritance" with no mention of state.

7. TYPE ERASURE
--------------------------------------------------------------------------------

Q: What is type erasure?

ANSWER
  Generics exist only at compile time. The compiler checks types, then erases
  them to Object (or to the declared bound) and inserts the necessary casts.
  It exists for backward compatibility with pre-Java-5 code.

  Consequences
    - List<String> and List<Integer> are the same class at runtime.
    - You cannot write "new T[]".
    - You cannot write "x instanceof List<String>".
    - You cannot overload two methods that differ only by type parameter -
      their erased signatures collide.
    - There is no T.class; you must pass a Class<T> if you need the type.

FOLLOW-UPS
  - What are the wildcards "? extends T" and "? super T" for?
    (PECS - Producer Extends, Consumer Super.)
  - What is a raw type and why is using one dangerous?
  - How do frameworks like Jackson recover generic type information?
    (Class metadata retains generic signatures - TypeReference / super type
    tokens.)

RED FLAGS
  - Believing generic type information is available at runtime.

8. MANY READERS, FEW WRITERS - READ/WRITE LOCK
--------------------------------------------------------------------------------

Q: How would you protect a data structure that is read by many threads and
   written by few?

ANSWER
  ReentrantReadWriteLock
    - Many readers may hold the read lock concurrently.
    - A writer holds the write lock exclusively - it blocks all readers.

  Things to watch for
    - Always release in a finally block.
    - Writer starvation with the default non-fair policy; "new
      ReentrantReadWriteLock(true)" is fair but slower.
    - You can DOWNGRADE write -> read (acquire read while holding write, then
      release write). You cannot UPGRADE read -> write - it deadlocks.
    - Read/write locks only pay off when reads are frequent and hold the lock
      long enough to matter; otherwise plain synchronized is faster.

  Modern alternatives
    - ConcurrentHashMap - lock-free reads, no explicit locking needed.
    - Immutable snapshots / CopyOnWriteArrayList for read-mostly data.
    - StampedLock with optimistic reads for very short read sections.

FOLLOW-UPS
  - Why can you not upgrade a read lock to a write lock?
  - What is reentrancy and why does it matter?
  - When would ConcurrentHashMap be the better answer than any lock?

RED FLAGS
  - Reaching for a read/write lock where ConcurrentHashMap or an immutable
    object would remove the problem entirely.
  - Not releasing the lock in finally.

9. equals() AND hashCode()
--------------------------------------------------------------------------------

Q: Where are equals/hashCode used? What is the contract between them? What
   happens if you do not implement them?

ANSWER
  Where they come from
    Both are defined on java.lang.Object, so EVERY object already has them.
    The defaults are:
      equals()    reference identity - same object in memory (like ==).
      hashCode()  a number derived from the object's identity (historically
                  the memory address; today a value stored in the object
                  header). Two equal-looking objects get different values.

  Where they are used - the main example
    Hash-based collections: HashMap, HashSet, LinkedHashMap, ConcurrentHashMap,
    Hashtable. This is how HashMap gets its O(1):

      1. put(key, value) -> compute key.hashCode()
      2. map the hash to a bucket index (hash % table length, after spreading)
      3. inside that bucket, walk the (short) chain and compare with equals()
         to find an existing entry with the same key

    So hashCode() picks the bucket -> that is the O(1) part.
       equals()   confirms identity inside the bucket -> that is correctness.

    Also used by: List.contains / indexOf / remove, Set uniqueness,
    Objects.equals, assertEquals in tests, distinct() in streams,
    String switch, and caches.

  THE CONTRACT (the basic rule)
    1. If a.equals(b) is true, then a.hashCode() == b.hashCode(). MUST hold.
    2. The reverse is NOT required - unequal objects MAY share a hash code
       (a collision). Collisions are legal, just slower.
    3. hashCode() must be consistent: same object, unchanged state -> same
       value every call within one JVM run.
    4. equals() must be reflexive, symmetric, transitive, consistent, and
       x.equals(null) must be false.
    5. Practical rule: ALWAYS override them together, and derive both from the
       SAME fields.

  What happens if you DON'T implement them
    You inherit Object's identity-based versions, so:

      Map<Point, String> m = new HashMap<>();
      m.put(new Point(1,1), "a");
      m.get(new Point(1,1));      // -> null !

    Two logically equal objects have different hash codes, land in different
    buckets, and are never compared. Symptoms:
      - HashMap.get returns null for a key that "is there"
      - HashSet holds duplicates
      - list.contains(x) is false although an equal element exists
      - "remove() does nothing"
    And the mirror bug: override equals() but NOT hashCode() -> objects are
    equal but hash to different buckets -> same broken behaviour. This is the
    single most common Java bug of this family.

  What is important in a hash function
    - CORRECTNESS FIRST: consistent with equals, computed from the same fields.
    - Good distribution / low collision rate. In the worst case every key
      collides and HashMap degrades from O(1) to O(n) (O(log n) since Java 8,
      which treeifies a long bucket chain when keys are Comparable).
    - Cheap to compute - it runs on every get/put.
    - STABLE while the object is in the map. Use IMMUTABLE fields. Mutating a
      field that participates in hashCode after inserting the object makes it
      unreachable - it sits in the old bucket forever (a real memory leak).
    - Use all the distinguishing fields, and only fields that equals() uses.
      Never include a mutable/derived/random field or the identity hash.
    - The classic 31*h + field formula (odd prime, JIT-friendly: 31*h ==
      (h<<5)-h). Just use Objects.hash(a, b, c) - but note it allocates an
      array and boxes, so hot paths sometimes hand-roll it.
    - It must not return a constant. "return 1" is technically legal (contract
      satisfied!) but turns every HashMap into a linked list.
    - A hashCode is NOT unique, NOT a database ID, and NOT stable across JVM
      runs or across versions - never persist it.

  Canonical implementation

      @Override public boolean equals(Object o) {
          if (this == o) return true;                     // fast path
          if (o == null || getClass() != o.getClass()) return false;
          Point p = (Point) o;
          return x == p.x && y == p.y;                    // same fields...
      }
      @Override public int hashCode() {
          return Objects.hash(x, y);                      // ...as here
      }

    Or just use a record - Java 16+ generates equals/hashCode/toString from
    the components for you. Lombok's @EqualsAndHashCode does the same.

FOLLOW-UPS
  - Two objects have the same hashCode. Are they equal?  (No - collision.)
  - Two objects are equal. Must they have the same hashCode?  (Yes.)
  - Is "return 0" a legal hashCode?  (Legal, but destroys performance.)
  - Why must a HashMap key be immutable?
  - getClass() vs instanceof in equals - what breaks with inheritance?
    (instanceof can break symmetry; getClass() breaks with proxies/Hibernate.)
  - Why is HashMap not thread-safe, and what used to happen on resize?
  - How does HashMap handle collisions?  (Chaining -> red-black tree at 8+.)

RED FLAGS
  - Overriding equals but not hashCode.
  - "hashCode must be unique."
  - Writing "public boolean equals(Point p)" - that OVERLOADS instead of
    overriding, and collections will never call it. (@Override catches this.)
  - Using mutable fields in hashCode.

10. equals() vs ==
--------------------------------------------------------------------------------

Q: What is the difference between equals() and ==?

ANSWER
  ==        An operator. Compares the VALUE OF THE VARIABLE.
              - primitives  -> compares the actual value (5 == 5)
              - references  -> compares the reference, i.e. "is this the very
                               same object in memory?"
            Cannot be overridden. Fast.

  equals()  A method on Object. Compares LOGICAL EQUALITY, however the class
            defines it. Object's default implementation is "return this == o",
            so if the class does not override it you get == behaviour anyway.

  The classic example

      String a = new String("hi");
      String b = new String("hi");
      a == b          // false - two distinct objects
      a.equals(b)     // true  - same characters

      String c = "hi";
      String d = "hi";
      c == d          // TRUE - both interned in the string pool

    That "sometimes true" is exactly why == on strings is a landmine: it works
    for literals and fails for anything built at runtime (new, concat,
    substring, StringBuilder, input read from a socket). Never use == on
    Strings.

  Boxing trap

      Integer x = 127, y = 127;   x == y   // true  - Integer cache -128..127
      Integer x = 128, y = 128;   x == y   // false - outside the cache
      Integer i = 128; int j = 128;  i == j  // true - i is UNBOXED, value compare

    Rule: == between two wrappers is a reference compare; == between a wrapper
    and a primitive unboxes and compares values (and NPEs if the wrapper is
    null).

  When == IS the right tool
    - primitives
    - enums (each constant is a singleton; == is null-safe and typo-proof)
    - deliberate identity checks: the "this == o" fast path in equals(),
      x == null

  Null safety
    a == null          fine
    a.equals(b)        NPE if a is null
    Objects.equals(a,b)  null-safe, use it
    "yes".equals(x)    Yoda style - constant first, cannot NPE

  Note: for arrays, equals() is still identity. Use Arrays.equals /
  Arrays.deepEquals. For BigDecimal, equals() also compares SCALE
  (2.0 vs 2.00 are not equal) - use compareTo() == 0.

FOLLOW-UPS
  - Why does "hi" == "hi" return true but new String("hi") == "hi" false?
  - What is the string pool / String.intern()?
  - What does == do for enums, and why is it preferred there?
  - Integer.valueOf(127) == Integer.valueOf(127)?  And 128?

RED FLAGS
  - Comparing Strings with ==.
  - "equals compares content, == compares content for primitives" without
    being able to explain the reference case.

11. JAVA GENERICS
--------------------------------------------------------------------------------

Q: What are generics and why do we use them?  (See also #7, type erasure.)

ANSWER
  What
    Parameterised types - a class, interface, or method takes a type as an
    argument: List<String>, Map<K,V>, Optional<T>.

  Why
    - COMPILE-TIME type safety. Errors move from runtime to compile time.
    - No casts. Before generics:
          List l = new ArrayList();
          l.add("hi");
          String s = (String) l.get(0);   // cast, and a ClassCastException
                                          // waiting to happen
      With generics the compiler guarantees it.
    - Self-documenting APIs and better IDE support.
    - Code reuse: one implementation for many types.

  Where you can use them
    Class      class Box<T> { private T value; T get(){return value;} }
    Interface  interface Repo<T, ID> { Optional<T> findById(ID id); }
    Method     static <T> List<T> listOf(T... items) { ... }
               (the <T> goes before the return type)

  Bounded type parameters
    <T extends Number>              T must be Number or a subclass
    <T extends Comparable<T>>       T must be comparable to itself
    <T extends A & B>               multiple bounds, class first
    A bound gives you the bound's methods inside the generic code.

  Wildcards and PECS
    List<?>              unknown type - you can read Objects, you cannot add
                         anything except null.
    List<? extends T>    PRODUCER - you READ T out of it. Cannot add.
                         (A List<? extends Number> might really be a
                          List<Integer>, so adding a Double is unsafe.)
    List<? super T>      CONSUMER - you WRITE T into it. Reads give Object.

    PECS: Producer Extends, Consumer Super.
      void copy(List<? extends T> src, List<? super T> dst)

  Invariance - the big gotcha
    List<String> is NOT a List<Object>, even though String IS an Object.
    Generics are INVARIANT. If it were allowed:
        List<Object> o = stringList;   // if legal...
        o.add(42);                     // ...heap pollution
    Arrays, by contrast, ARE covariant (Object[] o = new String[1];) which is
    why they throw ArrayStoreException at runtime. Generics catch it at
    compile time instead - that is the improvement.

  Erasure consequences (details in #7)
    No new T[], no T.class, no instanceof List<String>, no static field of
    type T, cannot catch a generic exception type.

FOLLOW-UPS
  - Why is List<String> not a subtype of List<Object>?
  - When would you use ? extends vs ? super?  Give a signature.
  - What is a raw type and why does it disable ALL generic checks in the
    method (not just for that variable)?
  - What is heap pollution / the @SafeVarargs warning?
  - How do you get a generic array?  ((T[]) new Object[n], plus @SuppressWarnings.)

RED FLAGS
  - Using raw types (List instead of List<String>) in new code.
  - Thinking generics have any runtime representation.
  - Sprinkling @SuppressWarnings("unchecked") without knowing why.

12. FUNCTIONAL INTERFACES (and lambdas)
--------------------------------------------------------------------------------

Q: What is a functional interface?

ANSWER
  Definition
    An interface with EXACTLY ONE abstract method (SAM - Single Abstract
    Method). That is the whole rule. It can then be implemented by a lambda
    or a method reference.

        @FunctionalInterface
        interface Validator { boolean test(String s); }

        Validator v = s -> s != null && !s.isBlank();   // lambda
        Validator w = String::isBlank;                  // method reference

  @FunctionalInterface
    Optional. It does not make the interface functional - the single abstract
    method does. It just makes the compiler FAIL if someone later adds a
    second abstract method, protecting every lambda that uses it. Use it.

  What does NOT count toward the single-method rule
    - default methods (any number)
    - static methods
    - private methods (Java 9+)
    - public abstract methods that redeclare an Object method
      (equals, hashCode, toString) - that is why Comparator, which declares
      both compare() and equals(), is still a functional interface.

  The built-in ones (java.util.function) - know these
    Function<T,R>      R apply(T)          transform          .andThen .compose
    BiFunction<T,U,R>  R apply(T,U)
    Predicate<T>       boolean test(T)     filter             .and .or .negate
    Consumer<T>        void accept(T)      side effect        .andThen
    Supplier<T>        T get()             lazy produce / factory
    UnaryOperator<T>   Function<T,T>
    BinaryOperator<T>  BiFunction<T,T,T>   reduce
    Older ones that qualify: Runnable, Callable<V>, Comparator<T>.
    Primitive variants (IntPredicate, ToIntFunction, IntUnaryOperator...)
    exist to avoid boxing in hot loops.

  Lambda vs anonymous class - worth knowing
    - "this" inside a lambda is the ENCLOSING instance; inside an anonymous
      class it is the anonymous instance.
    - A lambda does not create a new scope - you cannot shadow a local
      variable; an anonymous class can.
    - A lambda compiles to invokedynamic + a method, not to a separate
      Foo$1.class file. A stateless lambda is typically instantiated once.
    - Captured local variables must be final or "effectively final" - the
      value is copied. That is why you cannot mutate a counter from a lambda
      (use AtomicInteger, or better, a stream reduction).

  Where you meet them
    Streams (map/filter/reduce), Optional (map/ifPresent/orElseGet),
    CompletableFuture, forEach, computeIfAbsent, event/callback APIs,
    Comparator.comparing.

FOLLOW-UPS
  - Is Comparator a functional interface? It has two abstract methods.
    (Yes - equals() is an Object method and does not count.)
  - Can a functional interface have default methods?  (Yes, any number.)
  - Lambda vs method reference - when can you use a method reference?
    (Static, instance-of-a-particular-object, instance-of-an-arbitrary-object
     String::length, and constructor ArrayList::new.)
  - Why must captured variables be effectively final?
  - Supplier vs the value itself - why does orElseGet beat orElse sometimes?
    (orElse always evaluates its argument; orElseGet is lazy.)

RED FLAGS
  - "A functional interface is any interface with only one method" - it is
    one ABSTRACT method.
  - Thinking @FunctionalInterface is required.
  - Mutating shared state from inside a lambda in a parallel stream.

13. ACCESS MODIFIERS - WHO CAN CALL THIS METHOD?
--------------------------------------------------------------------------------

Q: What are the access modifiers, exactly who can access each one, and when do
   you use which?

ANSWER
  THE FOUR LEVELS - narrowest to widest

    modifier          same    same     subclass in    everyone
                      class   package  ANOTHER pkg    else
    ------------------------------------------------------------
    private            yes      no          no          no
    (none) "package-   yes     yes          no          no
     private"/default
    protected          yes     yes         yes*         no
    public             yes     yes         yes         yes

    * protected = "package + subclasses". Note it INCLUDES package access -
      protected is strictly wider than default, not a different direction.

  THE protected SUBTLETY (a real interview question)
    A subclass in another package may access a protected member only THROUGH
    A REFERENCE OF ITS OWN TYPE (or a subtype) - it inherits the right, it
    does not get to poke at other instances:

        package b;
        class Child extends a.Parent {
            void m(Parent other, Child sibling) {
                this.value   = 1;   // OK - inherited
                sibling.value = 1;  // OK - Child or subtype
                other.value  = 1;   // COMPILE ERROR - a plain Parent
            }
        }

  WHERE EACH APPLIES
    Top-level class/interface  -> only public or package-private.
                                  (private/protected are illegal there;
                                   NESTED classes may use all four.)
    Interface members          -> implicitly public. Since Java 9 an
                                  interface may also have private methods
                                  (helpers for default methods, see #6).
    Constructor private        -> no external instantiation: singletons,
                                  static factories (Optional.of), utility
                                  classes.

  USE CASES - the rule is "as private as possible"
    private
      DEFAULT for fields and for helper methods. Encapsulation: you can
      rename, change or delete it tomorrow because nobody outside can depend
      on it. ALL mutable fields should be private (plus final where possible).
    package-private (no keyword)
      For collaboration inside one package/module without exposing it. Also
      the classic way to expose something FOR TESTS in the same package
      ("@VisibleForTesting") - better than making it public.
    protected
      Only when you are DESIGNING FOR INHERITANCE: a hook or extension point
      a subclass is meant to override or call (template-method pattern -
      AbstractList.removeRange, ResponseEntityExceptionHandler's handlers).
      A protected member is public API for every subclass ever written, so it
      must be documented and kept stable. If a class is not designed for
      extension, make it final and skip protected entirely.
    public
      Your deliberate, supported API. Every public method is a promise you
      must keep. Changing or removing one breaks callers you cannot see.

  Why it matters beyond style
    Narrow access = a smaller surface to test, to document, to keep
    backward-compatible, and fewer places a bug can reach. It is also
    security-relevant: a public method is reachable by any code in the JVM.

  NON-ACCESS MODIFIERS - often asked in the same breath
    static        belongs to the CLASS, not an instance. One copy, no "this".
                  Utility methods, constants, factories.
    final         class: cannot be subclassed; method: cannot be overridden;
                  field: assigned once (reference is fixed, the OBJECT may
                  still be mutable); local/parameter: cannot be reassigned.
    abstract      class: cannot be instantiated; method: no body, subclass
                  must implement. Mutually exclusive with final and private.
    synchronized  method-level locking (see #14).
    volatile      field visibility/ordering (see #4).
    transient     skip this field during Java serialization.
    native        implemented in C/C++ via JNI.
    strictfp      (pre-Java 17) portable floating point.
    default       interface method with a body (see #6) - a keyword, not an
                  access modifier.

  Beyond the class: MODULES (Java 9+)
    A public type in a package that a module does not "exports" is still
    unreachable from other modules. So the real answer to "who can call
    this?" is "access modifier AND module exports". Worth a sentence if you
    are asked about JPMS.

FOLLOW-UPS
  - Is protected wider or narrower than default?  (Wider - it adds subclasses
    in other packages.)
  - Can a top-level class be private?  (No - only a nested one.)
  - Can you REDUCE visibility when overriding a method?  (No - you may only
    widen it. Narrowing would break the Liskov substitution principle.)
  - Why are interface methods implicitly public?
  - How do you expose a method for testing without making it public?
  - final field vs immutable object - what does final actually guarantee?
  - Can a private method be overridden?  (No - it is not inherited; you get
    a NEW method that hides nothing. Also not polymorphic, and not proxyable
    by Spring.)

RED FLAGS
  - public fields.
  - Everything public "because it is easier".
  - Thinking protected means "subclasses only".
  - Believing final on a field makes the object immutable.

14. synchronized: BLOCK vs METHOD, INSTANCE vs CLASS
--------------------------------------------------------------------------------

Q: What is the difference between a synchronized method and a synchronized
   block? What object is actually locked? (See also #3.)

ANSWER
  WHAT IS LOCKED - EVERY object has a MONITOR (an intrinsic lock). The
  question is always "which object's monitor?"

    synchronized instance method   -> locks  this
    synchronized static method     -> locks  MyClass.class  (the Class object)
    synchronized (obj) { ... }     -> locks  obj - whatever you name

  So these two are EXACTLY equivalent:

      synchronized void m() { body; }
      void m() { synchronized (this) { body; } }

  And these two are equivalent:

      static synchronized void s() { body; }
      static void s() { synchronized (MyClass.class) { body; } }

  THE KEY CONSEQUENCE - INSTANCE AND STATIC LOCKS ARE DIFFERENT LOCKS
    A thread in a synchronized instance method and a thread in a static
    synchronized method DO NOT exclude each other - they hold two unrelated
    monitors (the instance vs the Class object). If both touch the same
    static field, you still have a race. Guard shared STATIC state with the
    CLASS lock, and per-instance state with the INSTANCE lock; never mix.
    Likewise, two different instances have two different monitors, so
    synchronized instance methods give you no protection over static or
    shared data.

  METHOD vs BLOCK - why blocks are usually better
    1. SCOPE / granularity. The method form locks for the WHOLE method,
       including the slow parts that need no locking:

           synchronized void handle(Req r) {
               var parsed = parse(r);            // pure CPU, no shared state
               var remote = http.call(parsed);   // NETWORK - lock held!!
               synchronized (this) { cache.put(...); }   // <- only this needs it
           }
       Hold a lock for as little as possible, and NEVER across I/O.
    2. CHOICE OF MONITOR. A synchronized method locks "this", and "this" is
       PUBLIC - any other code holding a reference to your object can
       synchronize on it and interfere with (or deadlock) you. A private
       lock object cannot be touched from outside:

           private final Object lock = new Object();
           void add(String s) { synchronized (lock) { list.add(s); } }

       This is the recommended idiom. You can also use SEPARATE locks for
       independent state (lock striping) so readers of A do not block
       writers of B.
    3. Documentation: a block shows exactly WHICH state is protected.

  WHAT synchronized GUARANTEES (both forms)
    - MUTUAL EXCLUSION: one thread at a time per monitor.
    - VISIBILITY / happens-before: everything written before releasing the
      monitor is visible to the next thread that acquires the SAME monitor.
      Two threads using DIFFERENT locks get neither guarantee.
    - REENTRANCY: a thread already holding a monitor can re-acquire it, so a
      synchronized method may call another synchronized method on the same
      object without deadlocking itself.

  WHAT IT DOES NOT DO
    - It does not make the object thread-safe by itself: if a getter is
      unsynchronized, or a caller does check-then-act across two calls
      ("if (!map.containsKey(k)) map.put(k,v)"), you still have a race. The
      COMPOUND action must be inside one synchronized region.
    - It does not help if some code paths ignore the lock. A lock is a
      convention: every access to the guarded state must use it.

  NEVER LOCK ON
    - a String literal or a boxed Integer/Boolean - they are INTERNED and
      shared JVM-wide, so unrelated code may share your lock
    - a field you reassign (you would be locking different objects over time)
    - "this" in a class you hand out to untrusted/foreign code
    Prefer: private final Object lock = new Object();

  Deadlock
    Two threads acquiring two locks in opposite order. Avoid by imposing a
    consistent GLOBAL LOCK ORDER, holding one lock at a time, or using
    tryLock with a timeout (ReentrantLock).

  MODERN ALTERNATIVES - "would you use synchronized at all?"
    ReentrantLock           tryLock, timeouts, interruptible, fairness,
                            multiple Conditions; must unlock in finally
    ReadWriteLock/StampedLock  many readers, few writers (see #8)
    AtomicInteger/LongAdder every counter you were about to synchronize
    ConcurrentHashMap       computeIfAbsent/merge instead of locking a map
    Immutable objects       no shared mutable state, no lock needed
    Confinement             keep the state in one thread / one actor
    The best synchronized block is the one you deleted by removing shared
    mutable state.
    (Java 21 note: synchronized used to PIN a virtual thread to its carrier;
     ReentrantLock did not. Largely fixed in Java 24, but it is why library
     code moved away from synchronized.)

FOLLOW-UPS
  - Two threads, one in a synchronized instance method and one in a static
    synchronized method of the same class - do they block each other?  (No.)
  - Rewrite "synchronized void m()" as a block. What is it locking?
  - Why lock on a private final Object instead of this?
  - Is synchronized reentrant?  (Yes.)
  - Does synchronized give visibility as well as exclusion?  (Yes - unlike
    a plain field, and unlike using two different locks.)
  - What is wrong with synchronizing on a String constant?
  - synchronized vs ReentrantLock - when would you switch?
  - Is "synchronized Map get + put" safe?  (Not as two calls - the check and
    the act must be in ONE synchronized region, or use computeIfAbsent.)

RED FLAGS
  - Locking the whole method when two lines need it - especially around I/O.
  - Assuming static and instance synchronized methods exclude each other.
  - synchronized on a mutable field, a String literal, or a boxed value.
  - Believing "synchronized somewhere in the class" makes the class
    thread-safe.

15. RECORDS AND IMMUTABILITY
--------------------------------------------------------------------------------

Q: What is a record? What does immutable mean, and why do we want it?

ANSWER
  RECORD  (Java 16+)
    A compact, transparent carrier for data. One line replaces ~60:

        public record Point(int x, int y) {}

    The compiler generates:
      - private FINAL fields x, y
      - a canonical constructor Point(int, int)
      - accessors named x() and y()   (NOT getX() - no JavaBean prefix)
      - equals() and hashCode() from ALL components (see #9)
      - toString() -> "Point[x=1, y=2]"

    Validation / normalization goes in a COMPACT CONSTRUCTOR:

        public record Range(int from, int to) {
            public Range {                        // no parameter list
                if (from > to) throw new IllegalArgumentException();
            }
            public int length() { return to - from; }   // extra methods OK
            public static Range of(int a, int b) {...}  // static factory OK
        }

    Rules / limits
      - implicitly FINAL; cannot extend anything (it already extends Record)
      - CAN implement interfaces
      - no additional INSTANCE fields - only the components
      - you may override any generated member if you need to
      - works with pattern matching:  if (o instanceof Point(int x, int y))
      - Jackson supports them; JPA @Entity does NOT (entities need a no-args
        constructor and mutability)

    USE FOR: DTOs, API request/response bodies, events, value objects, map
    keys, method return tuples, config properties (#see the Spring file).
    NOT FOR: JPA entities, or anything with identity and a lifecycle.

  IMMUTABLE vs MUTABLE
    Immutable = state cannot change after construction. String, Integer and
    the other wrappers, LocalDate/Instant, BigDecimal, and records - but a
    record is only as immutable as its components (SHALLOW - see below).
    Mutable = StringBuilder, ArrayList, HashMap, your typical entity.

    SHALLOW vs DEEP IMMUTABILITY
      SHALLOW  the FIELDS cannot be reassigned, but the OBJECTS they point
               at may still change. The reference is frozen; the thing at
               the end of it is not.
      DEEP     everything reachable from the object is immutable too.
      A record whose components are only primitives, String, LocalDate,
      BigDecimal or other records is ALREADY deeply immutable. The
      distinction only bites when a component is itself mutable - a List,
      a Map, an array, a Date, or one of your own mutable classes.

    HOW TO MAKE A CLASS IMMUTABLE
      1. class final (or all constructors private) - no subclass can add
         mutable state or override behaviour
      2. all fields private final
      3. no setters, no method that mutates state
      4. DEFENSIVE COPIES in and out for any mutable component:

           public final class Team {
               private final List<String> members;
               public Team(List<String> members) {
                   this.members = List.copyOf(members);      // copy IN
               }
               public List<String> members() { return members; }  // unmodifiable
           }

    THE RECORD CAVEAT - records are SHALLOWLY immutable
      A record's components are final, so nobody can swap "members" for a
      different list. But nothing stops them mutating the list itself:

          record Team(String name, List<String> members) {}

          var t = new Team("A", new ArrayList<>(List.of("ann")));
          // t.members = otherList;    impossible - final, and no setter
          t.members().add("bob");   // COMPILES AND WORKS - not immutable

      So t now "contains" [ann, bob] although the record itself never
      changed. That is what SHALLOW means.

      Fix it with a defensive copy in the compact constructor:
          record Team(String name, List<String> members) {
              Team { members = List.copyOf(members); }   // now deeply immutable
          }
      Same trap for arrays, Date, and any mutable object you hold - copy
      them on the way in (and on the way out if you return them).

    WHY IMMUTABILITY
      - THREAD-SAFE for free: no writes means no races, no locks (#14)
      - safe as a HashMap key - the hash can never go stale (#9)
      - no defensive copying needed when you pass it around; no "who changed
        my object?" debugging
      - easier to reason about, test and cache
      - failure atomicity: a half-updated object cannot exist

    COST / WHEN MUTABLE IS FINE
      Every "change" allocates a new object. For hot loops or big structures
      that is real (the classic: String concatenation in a loop -> use
      StringBuilder). Local, single-threaded, short-lived state is fine
      mutable. The rule of thumb: IMMUTABLE BY DEFAULT, mutable where you
      have measured a reason.

    Related tools
      List.of / Map.of / Set.of         immutable factories (reject nulls)
      List.copyOf                       immutable copy
      Collections.unmodifiableList(l)   a VIEW - the backing list can still
                                        be changed by whoever holds it
      Arrays.asList                     FIXED-SIZE but writable - not immutable
      "final" is not "immutable"        final fixes the REFERENCE only (#13)

FOLLOW-UPS
  - What does a record generate for you?
  - Is a record always immutable?  (Only shallowly - see the Team example.)
  - Can a record extend a class? Implement an interface?  (No / yes.)
  - Why is String immutable?  (Security, the string pool, cached hashCode,
    thread safety.)
  - final field vs immutable object - what is the difference?
  - unmodifiableList vs List.copyOf?
  - Why is an immutable object safe as a HashMap key?
  - Would you use a record as a JPA entity?  (No.)

RED FLAGS
  - "final means immutable".
  - Exposing an internal List/array straight from a getter.
  - Records with mutable components and no defensive copy.
  - Records used as JPA entities.
